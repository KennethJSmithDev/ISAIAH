# Interoperability exploration candidate

The standalone harness reads a separately authorized session's recorded message headers. Its trace response and `isaiah run show <id>` can derive an `observations` summary from those retained headers: observed endpoint names, raw status counts and recorded error markers. This is a view of that session, not a production inventory or a current queue-health measurement. It never establishes delivery. No additional IRIS read is made to derive the summary, and it is not a new authorization or approval.

The local CLI can also show short starter lessons without inference: `isaiah explain --topic monitor`, `adapters`, `hl7`, `fhir`, or `dicom`. The three healthcare-format starters use the IRIS for Health documentation profile; the standard-IRIS profile reports those starters unavailable rather than asserting platform support. All use version-labeled InterSystems documentation. These are explanations, not proof about an individual production.

In a disposable IRIS for Health Build 154U fixture, the existing scoped MCP trace reader returned headers for a synthetic HL7 v2 message, a synthetic `HS.FHIRServer.Interop.Request`, and a generated synthetic DICOM document; each header was checked against an independent IRIS record. The restricted reader refused an unapproved session. This demonstrates header tracing for those specific message objects. It does not demonstrate an HL7 acknowledgment, a FHIR server exchange, an external DICOM/PACS transfer, an external delivery receipt, or general support for these formats.

The offline sender-contract experiment compares the factual verifier result with separately supplied synthetic contract fixtures. It distinguishes a permissible predicate proposal, an incoming-priority discrepancy and missing or conflicting contract authority. The experiment exercises these distinctions offline. The deployed gate owns authority for the bounded synthetic R17 action. [Reviewed sender-contract gate](interop-connections.md#sender-contracts-and-consequential-changes)

No patient or production data is required for these fixtures. A recorded header and a model explanation cannot establish an external outcome. Installations must grant each target and action separately and preserve the existing audit and approval boundaries.
